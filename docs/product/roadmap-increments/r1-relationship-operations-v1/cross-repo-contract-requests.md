### A.1 — ADR-111 is at rev 5, and three of the repairs are yours

*Added 2026-09-19.* ADR-111 was **ratified at rev 2** and has since been repaired to **rev 5**, all on 2026-09-18, while Gu OS built the C2 endpoint against it. The repairs were made under the ratification clause's own terms — *"not to be reopened unless implementation exposes a concrete contradiction with the ratified contract"* — and **the mechanism, key-binding model, purposes, rotation model and interoperability fixture are unchanged.** Nothing below is a new decision; each is the ratified contract stated to the precision implementation demanded. **Build against rev 5.**

**1. `service` and `source_system` are authorization bindings, not metadata** (ADR-111 §6.1). Each endpoint declares exactly one required purpose **and** the caller/source it will accept. A key whose `purpose`, `service` or `legacy_source_scope.source_system` does not match is rejected `403` — **even though its signature is valid**. **C2 declares Traditional Gu (`traditional_gu` / `traditional_gu`) from this contract, never from the payload.** An `events-ingest` key cannot read authority; a `legacy-read` key cannot ingest events. Purpose scoping is the separation, and it is enforced rather than documented.

**2. Owner / source scope is established server-side, and it fails closed** (ADR-111 §6.3). The key record names the `source_system` and the Traditional Gu owner/source refs the caller may speak for. **An empty `ownerRefs` set authorizes no owner.** A `legacy_owner_ref` in the signed payload is a **consistency assertion only** — never authorization by itself — and omitting it does not widen the key. The actual owner of the requested Lead is derived from **server-observed source data** and checked against the key's server-side allowed scope; a claim that disagrees with the observed owner, or an observed owner outside the key, is `403`. **A Gu OS Lead → Case → Organization mapping does not substitute for that scope**: no Gu OS row stores a durable Traditional Gu owner UID, so the current server-observed source owner is the only owner-scope evidence there is ([`slice-plan.md`](slice-plan.md) §4, **SA-6.7**). Where the scope cannot be established, Gu OS returns `403`, records a security/operational audit, returns no C2 authority data, and creates no Case-scoped `authority_resolution`. **What this means for you: issue a key per pilot owner scope, and expect a `403` rather than a degraded answer when a key speaks for an owner it was not issued for.**

**3. C2 replay safety is semantic and keyed on the provider message id** (ADR-111 §8, repaired at revs 3–4). **There is no signature cache, and none is being asked for** — a process-local cache is unsound across instances and a shared durable one buys nothing. C2 is **not** read-only: SL-6 persists `unknown` and `conflicting` as `authority_resolutions`, so within-window replay is made harmless by durable-state identity instead. **The logical request identity is the provider message id already available at your pre-agent seam, after your provider-id dedup guard** ([`technical-plan.md`](technical-plan.md) Appendix D.3). Gu OS stores it as `authority_resolutions.provider_message_id`, **unique per Organization when present** — that is, the request identity is `(organization_id, provider_message_id)`. The consequences, which are the reason this is worth stating:

- retrying one logical authority-read inserts **no second durable incident**;
- a later **fail-safe** evaluation of the *same* logical request **reopens that row in place**, so the **current** fail-safe is what surfaces, with prior snapshots preserved in `provenance_jsonb.history`;
- a later confident `gu` / `human_active` observation **closes** unresolved incidents for that Case and opaque conversation ref together, when both are known, and inserts nothing;
- an existing row is **not** an idempotent retry if its Lead or Case identity conflicts with the current request.

**What this asks of you: send the provider message id, call after your dedup guard, and do not synthesize a fresh identity per retry.**

**4. Sign the declared path** (ADR-111 §3, repaired at rev 3). This began as a Gu OS implementation fact and has one consequence on the wire. Next.js 16 / undici expose `Request.url` **already collapsed** — `/api/legacy/../legacy/authority` and `%2e%2e` both become `/api/legacy/authority` — before the App Router handler runs, so the raw request-target is unobservable there. The route therefore verifies the **declared** path `/api/legacy/authority` and rejects a signature computed over any other representation. **Sign that exact path.** ADR-111 is explicit that this preserves *"only the declared route accepts a valid signature"* and does **not** preserve inbound observation of the exact request-target bytes; it must not be read as claiming otherwise.

*One further rev-5 repair is entirely ours, and is mentioned only so you do not read anything into our responses.* Pre-authentication rate limiting must not choose its bucket by whether a key exists, so every well-formed key id maps into a fixed-cardinality hashed bucket space and bucket selection cannot depend on key lookup. Known and unknown key ids are therefore indistinguishable before authentication — which is what keeps `401` from becoming a key-enumeration oracle (§7, §8). Raw presented identifiers are neither stored nor logged.

**B. Ratify the C1 integration-event architecture** — **DONE. Ratified as written at rev 4 on 2026-09-17** ([`slice-plan.md`](slice-plan.md) §8 **Q15**), so [ADR-112](../../../adr/ADR-112-cross-repo-integration-events.md) is **Accepted direction** and is the governing C1 contract. **So the second sentence to take to the Traditional Gu team: C1's event identity, envelope, normalized semantics and durable publication are settled too, and can be built against.** What it settles: **entity identity is not event identity**; **publication must be durable on the producer side**; **durability is not the same boundary as delivery-readiness**, so an appointment event whose Calendar or Firestore outcome is still unknown is not sent with those outcomes invented; **no delivery order is guaranteed, not even within one appointment**; and **exactly one finalization per event wins**, by compare-and-set rather than by sequencing the writer against the recovery sweep. All of it is detailed in §5 below, because it changes what you would build. Ratification authorizes no Gu OS code — SL-5 is not READY.

**C. Name who provisions and rotates the keys** — [`slice-plan.md`](slice-plan.md) §8 **Q16**. Repository evidence establishes the *mechanism* on both sides and not the *accountable owner* of a key spanning both estates. **Deferral re-affirmed on 2026-09-17 when A was ratified, so the original "behind A" sequencing no longer applies** — the shape is settled and only the name is open: one accountable owner across the two estates, with local custodians and implementers permitted on each side. A single owner is what makes ADR-111 §8's overlapping-key rotation executable, since two independent owners would have to synchronize a redeploy across both estates. Deliberately not a secrets-management redesign. **No secret value was inspected or recorded anywhere in this work.**

**Source precedence, recorded as a transitional fact about your system and not as a Gu OS invariant.** Mongo `gu2.appointments` is the **current primary operational representation** for appointments; the Firestore deal appointment is a **secondary/replicated** representation that may carry additional effect evidence. Divergence remains observable and is **never silently reconciled**. This precedence is transitional and may change if appointment ownership migrates to Gu OS.

**Lead context must compose, not choose.** Mongo is the more complete source for substantive lead data where both stores hold equivalent information — **but it is not a superset of Firestore.** Firestore carries operational assignment and ownership semantics (`assigned`, `assignedTo`, `assigned_at`, `assignment_type`, `assignation_type`, `new_assignment`, organization containment, advisor references, conversation structures) that are **not projected 1:1** into the Mongo `users` document, which in existing assignment flows instead carries fields like `owner_phone_number` and `owner_name`. So the response composes Mongo substantive data with Firestore assignment/ownership metadata, **with per-field provenance preserved**, and no read may discard Firestore assignment state on the grounds that Mongo is the preferred lead source. The real source model is asymmetric and capability-specific; *lead → Mongo, everything else → Firestore* is not a correct simplification of it.

**Appointments return both representations, never a fabricated single truth** — per-store presence and absence, per-store provenance, an explicit list of disagreements, and Firestore-specific effect evidence where present. *Corrected 2026-09-17:* Gu OS had assumed the Google Calendar identifier was **Firestore-only**. It is written by the legacy appointment creators to **both** stores (audit §24.3). That assumption was a live defect on our side — the Mongo normalizer discarded the field, blinding the orphaned-Calendar-effect check on the store that is actually canonical — and it is **repaired here** with fixture and selftest coverage. It is named because it would have produced a C6 response that looked clean and was wrong.

**Appointment persistence is currently partial and distributed, and the response must not hide that** to look tidier. Refusing or pairing explicitly is the correct behavior; guessing is not.

**What C6 landing actually retires**, and why the gate has no waiver: today Gu OS reads Traditional Gu's stores directly, under the `traditional_gu_firestore` and `traditional_gu_mongo` credentials recorded in [`sl1-legacy-read-credentials.md`](sl1-legacy-read-credentials.md). That is acceptable while every stage is shadow. SL-9 is the first stage that produces a prospect-facing external effect, and reading a broad project credential to decide an effect is the boundary TD-5 refuses to waive. **C6 is therefore not a performance or tidiness change — it is the condition under which Gu OS stops holding read access it should not hold once it can act.** **That transition is not claimed until it happens**: it requires C6 implemented on your side *and* the broad access removed on ours, under SL-9.

**Not C6, and worth saying so explicitly:** the Mongo lead runtime fields (`bypass_bot`, the assignment mirror) are **not** a read API. They arrive as C1 events and are consumed by C2. Asking for them here would build the wrong thing. Equally: this must stay **capability-bounded**. Generic collection access, or a generic Firestore/Mongo pass-through, is not a smaller version of C6 — it is the thing C6 exists to avoid.

***Added 2026-09-19, because two things on the Gu OS side could be mistaken for C6 progress and are not.*** **`bootstrap_direct` is not C6.** It is the sanctioned shadow-stage direct-adapter path that C6 exists to retire, every one of the four capabilities still runs on it, and no adapter has moved to `legacy_read_api`. ### 5.1 Event identity — the part that must be agreed, not assumed

**Entity identity is not event identity.** An entity id says *what* changed; an event id says *which mutation* happened.

- **`inbound_prospect_message`** — use the **provider (Meta) message id**. It is a durable logical message identity the provider already supplies, it is available at ingress, and inventing a UUID beside it would be strictly worse. *(It is currently available at ingress and persisted nowhere, which is why emitting at ingress is both the cheapest and the only reliable point.)*
- **Same-thread advisor activity** — the provider/echo message id where one exists.
- **`assignment_change` and `appointment_change`** — a stable `event_id` minted **once** for the logical mutation and **reused across every retry and delivery attempt**. Explicitly **not** the entity id, not `assigned_at`, not a database update timestamp, and not request arrival time. One appointment legitimately has many logical events — creation, reschedule, confirmation, cancellation, status transition — and identifying them by the entity collapses them into one.
  - *Corrected 2026-09-17:* an earlier draft of this section called the Mongo `_id` the canonical appointment entity identity. **It is not.** The event-facing entity identity is the **client-minted `appointment_id` business key** — the UUID created once at creation that every writer actually queries on — and the `_id` is incidental. ADR-112 §5 has this right; this document did not.

Gu OS derives its dedup key as `<sourceSystem>:<eventKind>:<externalRef>:<discriminator>` through `buildSourceEventDedupKey`, which lives in the shared types package *specifically* so the polling adapter and the C1 webhook cannot drift apart. **The `event_id` above is that discriminator.**

### 5.2 Normalized `assignment_change`

Treat assignment as **three concerns, not one**: organization membership and advisor eligibility; the legacy policy that chooses an advisor; and the resulting durable lead → advisor assignment. **C1 does not reproduce your assignment algorithms.** Traditional Gu remains the owner of assignment-selection policy in this phase, and Gu OS consumes the resulting semantic event.

Carry, where available: the stable `event_id`; the lead ref; the assigned advisor ref; the **previous** advisor ref *when it is genuinely known*; the semantic operation (`assignment` / `reassignment` / `unassignment`); the legacy policy provenance (`assignment_type` / `assignation_type` and the writer) when useful; `occurred_at`; and source provenance.

**Preserve absence rather than fabricating it.** Most writers do not read the previous assignee before overwriting it, so it is not reconstructable for them — the offboarding cascade is the clear exception, since the previous assignee is its query key. A field that is *sometimes* a guess is worse than a field that is sometimes null.

**Do not infer current assignment** from the Mongo owner name, the owner phone number, or a single `role_user` literal. On roles: the legacy vocabulary includes at least `vendedor`, `seller`, `admin` and `super-admin`, with different paths using different literals for the same concept. **Normalize the semantic role at the integration boundary** rather than propagating inconsistent literals into a durable contract — and note that `role_user == vendedor` is not by itself the eligibility rule, since existing logic also weighs organization membership and status. Carrusel is documented as **round-robin with legacy eligibility behavior** — ordered sellers, an order counter, wrap-around, skipping ineligible sellers — not as pure round-robin.

### 5.3 Normalized `appointment_change`

The **`appointment_id` business key** — client-minted at creation, stable for the appointment's whole life, and what every writer queries on — is the entity identity. The Mongo `_id` is incidental and is not the contract. Each logical mutation gets its own `event_id` (§5.1). Where a mutation also produces Firestore effects or replica changes, carry those as **secondary provenance/effect evidence**. Where a writer touches **only** Firestore, say so explicitly rather than implying the canonical Mongo appointment changed. **C1 is not the project in which the legacy appointment model is normalized**, and nothing here asks you to reconcile the two stores.

### 5.4 Durable publication — the one architectural ask

**A business mutation followed by a best-effort HTTP POST is not sufficient**, and this is the part of C1 that is a design ask rather than a wiring ask. The write commits, the process dies, and the event is never delivered — with nothing anywhere recording that it was owed.

So: **persist a durable integration record before attempting delivery**, and have the bridge drain it. The smallest useful record carries the `event_id`, event kind, external/entity ref, `occurred_at`, a **server-derived** organization/legacy scope (never caller-supplied), the bounded payload, provenance, delivery state, attempts, and last attempt/error. **This is not an event-sourcing platform and is not a request to become one** — one table, four event kinds, a drain loop. No projections, no replay-as-truth, no generic bus.

**Existing Pub/Sub may carry the delivery leg *after* the durable record exists; it cannot replace it.** Both main consumers acknowledge before doing the work, and one dead-letter topic has no subscription (audit §24.7), so Pub/Sub does not close the mutation-to-publish window — it moves it.

**Atomicity, stated per store rather than averaged:**

- **Assignment — atomic, achievable today.** The authoritative write is Firestore, `runTransaction` is already used in the codebase, and the integration record goes **inside the same transaction**. Writing it at an organization-scoped path makes the scope structural rather than a supplied value.
- **Appointments — two boundaries, not one.** A *separate* Mongo outbox collection cannot be transactional with the business write: the Atlas Data API is stateless HTTP and cannot join a multi-document transaction, and no session or transaction usage exists anywhere in the repository. But **every canonical appointment mutation is a write to exactly one appointment document, and Mongo is atomic at the single document, including through the Data API.** So the obligation is recorded **inside the appointment document**, in the same update as the business change — a `pending_integration_events` entry pushed, with no sequence counter. **After that the event cannot be lost.** What it can still be is *incomplete*, which is the second boundary:
  - **§7A, obligation durable.** Canonical mutation plus obligation, one atomic update. **This is the only thing that is single-document atomic — the logical appointment operation is not**, because it can also produce Calendar and Firestore effects that are transactional with nothing.
  - **§7B, finalized and delivery-ready.** The entry carries `state` (`pending` / `finalized`) and `awaiting`. It becomes deliverable only once every secondary outcome is observed or explicitly marked, and **the drain delivers finalized entries only.** Sending at §7A would mean fabricating outcomes still unknown, since the payload reports `store_write_outcomes` and `calendar_effect`.
  - **On thirteen of the fourteen writers this costs one write, not two**, because the verified ordering puts the canonical Mongo write last or alone: creation runs Calendar → Firestore → **Mongo**, cancellation ends at the **Mongo tombstone**, and the nine Mongo-only writers have no secondary effects at all. Those push `finalized` directly. **The exception is the prospect-side reschedule**, which writes Firestore, then **Mongo**, then Calendar, then **Mongo again** — and that second update, which the path already performs, carries the finalization. See [`legacy-source-audit.md`](legacy-source-audit.md) §24.3 for the ordering, verified against `gcp/main`.
  - **§7C, recovery.** A process that dies between the boundaries leaves a `pending` entry that a scan finds by definition. Recovery finalizes it with each unresolved outcome recorded as **`unknown`** — never `written`, `deleted`, `failed` or `not_attempted`, each of which would be a claim about what happened — and `finalized_by` records that recovery defaulted it rather than the writer reporting it. **`unknown` is a third state on the Gu OS side too:** neither *no effect* nor *failed*, and flattening it into either would hide the orphaned-Calendar case.
  - **What can still be lost is a mutation written by a path that bypasses the emission helper.** That is a **coverage** property, not a durability one — enumerable against the fourteen named appointment writers and enforced by a test, not by a sweep that cannot see what was never recorded. The sweep is two narrow checks over named fields: entries `pending` too long (recovery finalizes them) and entries `finalized` but undrained too long (drain liveness). It is not a lost-event detector and is not described as one.
  - **No sequence counter.** ADR-112 §7E removed the `integration_seq` an earlier revision proposed: the client-side read-then-increment-then-push it needed can race, letting two concurrent updates stamp the same value, and nothing in the Data API returns a post-increment value to the `$push` that depends on it. Nothing was needed in its place — the pending array's own non-emptiness is the liveness signal, and **`$push` append order durably records canonical mutation order**, which no client precomputes. Drain workers claim an entry with a single-document `findOneAndUpdate` so removing the counter opens no double-delivery hole.
  - **No delivery-order guarantee, including within one appointment** (§7F). Recording mutation order and delivering in it are different things: a later entry that finalized in one write is deliverable while an earlier `pending` one is not, so **a reschedule awaiting its Calendar outcome can be overtaken by a confirmation behind it.** Head-of-line delivery was considered and rejected, because one `pending` entry would stall every later event for that appointment and no Gu OS consumer needs the ordering. **Stay idempotent on `event_id`, and compare `occurred_at` to tell a stale mutation from a current one** — but note that `occurred_at` does *not* resolve disagreement between the two legacy stores, which spec S2 **EC-09** governs by requiring preserved uncertainty and provenance rather than last-write truth.
  - **Exactly one finalization per event, enforced rather than sequenced** (§7B/§7C-bis). The writer and the recovery sweep can both reach a `pending` entry, so finalization is a conditional single-document update filtered on `$elemMatch: { event_id, state: "pending" }` — a compare-and-set, so MongoDB picks the winner. **A no-match means someone else finalized it: treat that as success, not an error, and do not retry.** If the writer wins, recovery is a silent no-op. **If recovery wins, the late writer must not overwrite** — the event may already be delivered, and because Gu OS dedups on `event_id` a corrected redelivery would be silently dropped, so overwriting would leave the two sides permanently disagreeing. The real late outcome goes into a separate `late_outcome_observations` array as diagnostics; a rising count means the sweep's age threshold is firing while writers are still working, which is the thing to fix. Delivering corrections would be a new event kind and a new decision.
  - *Corrected twice, on 2026-09-17, in opposite directions — both worth knowing before building.* Rev 1 named a real process-death window and then called the result *at-least-once with a reconciliation backstop*, which that mechanism could not provide. Rev 2 fixed that and then treated a durable obligation as a **deliverable** event, which would have shipped confident falsehoods about Calendar and Firestore. **The guarantee is at-least-once for every event that reached §7A, with outcomes either reported or explicitly marked unreported — not exactly-once**, and duplicate delivery is expected and absorbed by `source_events` uniqueness.
- **Message ingress — covered by provider retry, conditional on one change.** Meta redelivers unacknowledged webhooks, so the ingress leg is durable **provided the receiver acknowledges only after the durable record exists.** The current webhook acknowledges before downstream processing (audit §7.2), so this is a requirement on the seam, not a property it has.

**Gu OS `source_events` remains a second, independent idempotency boundary.** Its Organization-scoped uniqueness protects us from duplicate delivery. It is **not** a substitute for producer-side durability: it can only deduplicate events that arrive.

### 5.5 `ungga-landing` is in scope for C1, and this was the other stale premise

*Corrected 2026-09-17:* the earlier working assumption that `ungga-landing` is a marketing front end is wrong, and correcting it adds work the assumption would have missed (audit §24.8). It is a server-rendered application with privileged direct access to both systems of record, and it writes state all three contracts care about: the organization's assignment policy, the guardia roster, the carrusel ordering, property→advisor assignment, appointments **directly in the canonical store**, and the flags a suppression decision would consult. It has **no event-emission infrastructure at all**.

Two consequences. **It needs C1 emission**, for the state it writes directly. But **assignment events must be emitted where the durable lead → advisor assignment changes** — for the manual path that is the `ungga-full` endpoint this repository proxies to, not the proxy. Emitting from the proxy would miss every other writer and double-count this one. It does **not** create leads (portal origination is a WhatsApp deep link and the backend creates the lead), so lead-creation events are not its concern.

**It needs nothing for C6** — the bounded reads are served from the `ungga-full` bridge — and **nothing for the advisory C2 call**, since it has no prospect-reply path to gate. It is, however, the **writer** of the authority flags, so whichever way C2 eventually sources them is work here at SL-11. Details in [`technical-plan.md`](technical-plan.md) Appendix D.5.

## 6. C2 — authority-aware routing

> **Owned by** [`technical-plan.md`](technical-plan.md) TD-3 and §4 (row C2), under [`ADR-107`](../../../adr/ADR-107-runtime-conversation-authority.md). **Gate:** advisory recording at your router, **enforcing at SL-11**. **Unblocks:** SL-11. **Implementation map:** [`technical-plan.md`](technical-plan.md) Appendix D.3. *Updated 2026-09-19: C2 no longer unblocks SL-6, which is Done without it — see immediately below.*

**C2 is the only one of the three with a deliberate two-step shape, and the step requested now is the harmless one:** the legacy router calls the endpoint and the answer is **compared, logged and not obeyed.** Enforcement is SL-11, a different stage and a separate decision.

***Corrected 2026-09-19 — and it changes who is waiting for whom.*** v0.5 said this advisory step unblocks SL-6. It does not, and it did not.

- **SL-6 is Done, and it never depended on C2.** The Accountable's resolution of [`slice-plan.md`](slice-plan.md) §8 **Q17** established on 2026-09-17 that nothing in SL-6's inspectable outcome required your router to call the endpoint, and **removed its `[L:C2 advisory]` marker** — the only marker ever removed from that table, and removed by decision rather than by reinterpretation. SL-6 proved its authority verdict through a bounded semantic read plus an independent oracle instead. **Please do not treat any C2 work as unblocking SL-6.**
- **The Gu OS endpoint already exists.** `POST /api/legacy/authority` is built, ADR-111 verifier and all, and is **inert until something calls it**.
- **What is missing is entirely yours:** the router-side invocation, and the router-side recording of the comparison. **That recording is C2** — it is what the contract is for, and the endpoint existing does not deliver it.
- **Enforcement remains SL-11** and is still not requested here.

So the honest statement of the ask is narrower than v0.5's: **C2 is on no Slice's critical path today**, because the Slice that would have consumed it advisory-side closed without it. It re-enters the critical path at **SL-11, enforcing**, behind SL-9 and SL-10. That is a reason to plan it deliberately rather than urgently — not a reason to drop it, since SL-11 cannot be reached without it.

**The request, in two parts that should not be conflated:**

1. **Advisory — call `POST /api/legacy/authority` before invoking the legacy agent, and ignore the answer.** Signed per ADR-111 (**rev 5**) with an `authority-read` key, **distinct from the events key**: purpose scoping means an events key cannot call this endpoint, and that separation is the point. Three rev-5 obligations land squarely on this call and are stated in full in **§3 A.1** — the key's `service` / `source_system` bindings (A.1 item 1), server-side owner-scope resolution that fails closed with `403` (item 2), and **semantic idempotency on the provider message id** rather than a signature cache (item 3). The last one is the one most easily missed: **send the provider message id and call after your dedup guard**, so one logical authority-read does not become two durable incidents.
2. **For SL-11 — suppress the automated legacy reply when the answer says Gu OS owns the interaction.** Not requested now. It is named here only so the SL-6 wiring is built with it in view.

**The seam.** Audit §24.6 places it in the Python runtime's main app, at the per-lead branch immediately before the agent is invoked and **after** the provider-id dedup guard — after, so a duplicate delivery does not produce a second advisory call for one message. The comparison is logged alongside the existing structured logging on that branch and **discarded for decision purposes**. **No organization entity is in scope at that point**, which is why the request carries opaque refs and never an organization claim; the Organization comes from the ADR-111 key binding.

**Constraints that come from the audit rather than from a preference, and getting either wrong would be worse than not shipping C2:**

- **`advisor_wa` / waProbe captures are evidence, never authority.** They are off-thread observations and do **not** set `bypass_bot` (audit §9.1, §9.1.1). Treating them as authority would hand a conversation to Gu OS on the strength of a side channel. The `advisor_activity` event of §5 must therefore be emitted from the **same-thread** echo branch only.
- **A human actively handling a conversation keeps it.** Suppression must respect the takeover state the audit describes in §8, including the resume window. ADR-107's rule is that conflict **fails safe**, and that transport is not authority.
- **Four concepts stay distinct** and must not be flattened into one: the assigned advisor; an organization member; a same-thread human takeover; and off-thread advisor evidence. The organization → advisor → lead relation may later enrich authority reasoning; it does not broaden SL-6.
- **The two `bypass_bot` fields are different things** — per-lead takeover in Mongo `users`, and a per-bot-number kill switch in `gunumbers` (audit §24.6). They stay distinct.

**One sequencing note.** The router C2 touches is the same one C5's WBA compatibility mechanism runs through ([`technical-plan.md`](technical-plan.md) Appendix C). C5 is not an R1 readiness dependency — established on evidence and repaired in Technical Plan v1.6 — but C2 work should be planned with it in view, because testing suppression on a pilot number that is not processable proves nothing.

## 7. Proving the contracts without a joint integration environment

**Owned by** [`technical-plan.md`](technical-plan.md) §8 and [ADR-111](../../../adr/ADR-111-legacy-service-auth-v1.md) §10–§11. Summarized here because it is the part that requires both sides to do something.

**TD-13 is proved against a shared fixture, not against each other's running systems.** [`td-13-legacy-service-auth-v1.test-vectors.json`](td-13-legacy-service-auth-v1.test-vectors.json) carries a fictional secret, two complete request descriptions (one POST with a body, one GET whose received query order differs from canonical order so an unsorted signer cannot pass), the exact raw body bytes as base64, the body hash, the **complete canonical signing string in both escaped and base64 form**, and the expected signature. The base64 rendering exists because the escaped form still requires agreeing what `\n` means, and a line-separator disagreement is the single most likely first-integration failure.

Each side implements independently and asserts against the file. **No shared runtime package is introduced** — a shared library across a Python/Node/two-repo boundary would couple deployments to avoid implementing thirty lines of HMAC twice. On our side the fixture is guarded by `npm run test:td-13-test-vectors`, which recomputes every derived value and additionally asserts the signature moves when the method, path, query, timestamp, key id, body or secret moves. **The protocol contract, not executable code, is the interoperability source of truth.**

**Rejection cases are specified rather than fixtured**, because a rejection has no canonical signature to agree on. ADR-111 §11 enumerates them; the ones most likely to be missed are that a **reordered query must still pass**, that a **parsed-and-re-serialized body must fail**, and that an **old key inside the rotation window must pass** while one after revocation must not.

**Two things worth copying from ADR-111 rather than re-deriving** — they entered at rev 2 and are unchanged at rev 5. The three header patterns are normative and live in a **fenced block, not a table** — a table cell requires a pipe to be backslash-escaped, and an earlier draft therefore published a timestamp pattern that, read from source, matches no ordinary epoch at all. And the query must be **printable ASCII, `0x21`–`0x7E`, rejected before canonicalization**: that precondition is what makes "sort by byte order" mean the same thing in Node and in Python, since without it UTF-16 and UTF-8 orderings diverge on supplementary characters. Under it you may use your language's default string sort.

**A third, from rev 3, is easy to miss because it reads like a Gu OS detail and is not.** The C2 route verifies the **declared** path `/api/legacy/authority`, because Next.js/undici collapse dot segments before the handler can observe the request-target. **Sign that exact path** (§3 A.1, item 4).

**Per contract, the behaviors both sides should cover** ([`technical-plan.md`](technical-plan.md) §8): for **C1**, that the same event retried under the same `event_id` yields one semantic Gu OS event, that two different logical mutations of the same entity stay distinct, that provider message ids deduplicate, and that neither assignment nor appointment identity rests on a timestamp; for **C2**, that the advisory call enforces nothing and that same-thread evidence is distinguishable from off-thread; for **C6**, that only the bounded capabilities are reachable, that a cross-Organization request is rejected, that lead composition preserves per-field provenance, that appointment disagreement stays visible, that advisor and Gu threads stay distinct, and that delivery status stays per message.
