## 1. Technical approach summary

Build the missing **cross-domain platform substrate first** (organization/identity, policy, authority, external bindings, gateway/eventing, relationships, effects ledger), then express Relationship semantics **entirely on the shared kernel** (case type + facts + Work + approvals + skills), then the S4 projection and economics — every step additive, per-organization flagged, and staged **shadow → assisted → selective live** on the Alebrixe pilot, following the repo's proven `advisory-first` / parallel-run / flag-off-rollback patterns. No Relationship-specific runtime, scheduler, retry engine, evidence store, approval store, cost table or portfolio SOR is introduced (anti-mini-app constraint holds throughout).

Two structural facts from the baseline shape everything: (a) tenancy is 100% `user_id` today, so ADR-106 is the first dependency of almost everything multi-seat; (b) there is **no fresh legacy read/write path** in Gu OS today (BigQuery mirrors only; no WhatsApp send), so AC-1/AC-2 seams are net-new and sequence-critical.

## 2. Technical Design decisions (TD-1 … TD-16)

### TD-1 — Organization, membership, contacts and external identity (ADR-106)
**Recommendation.** Six new org-scoped tables (TENTATIVE):
- `organizations` — id uuid, name, status, created/updated.
- `organization_memberships` — organization_id, user_id → profiles, role text (initial vocabulary `owner | org_admin | advisor`, mapped at migration time from legacy `super-admin`/`admin`/`vendedor`; not the permanent authorization model), `status` (`active | inactive` — **soft lifecycle: membership rows are never hard-deleted**, deactivation flips status so identity/provenance references stay resolvable), unique(org, user), plus `unique(id, organization_id)` as a composite-FK target.
- `external_identity_bindings` — organization_id, source_system (`traditional_gu`), binding_kind (`legacy_organization_key | legacy_user | gu_whatsapp_number | advisor_whatsapp_endpoint | legacy_lead | prospect_channel`), external_id (opaque text; never parsed). **Referential integrity — cross-tenant mismatches structurally impossible, not just non-dangling:**
  - typed nullable FK columns — `ref_organization_id`, `ref_membership_id`, `ref_contact_id`, `ref_case_id` — CHECK exactly one set (deliberate deviation from the CURRENT `artifact_inputs` no-FK precedent: this is a security boundary);
  - **same-org guarantees, all as real composite FKs (no triggers):** `ref_contact_id` → `(ref_contact_id, organization_id) REFERENCES contacts(id, organization_id)`; `ref_case_id` → `(ref_case_id, organization_id) REFERENCES operational_cases(id, organization_id)` (also structurally prevents binding a non-org case, whose `organization_id` is NULL; this composite-FK target requires `unique(id, organization_id)` on `operational_cases` — landed by M-CASE-ORG); `ref_organization_id` CHECK `ref_organization_id = organization_id`; person identity binds via **`ref_membership_id` → `(ref_membership_id, organization_id) REFERENCES organization_memberships(id, organization_id)`** — the membership row (soft-lifecycle, never hard-deleted) carries the person↔org pair, so the FK expresses same-org membership existence directly. **Identity ≠ authorization:** the binding stays historically true when the membership goes `inactive`; current authorization is always checked at action time against `status='active'` (`authorizeOrgAction` / `is_active_org_member`); inactive members' identities remain resolvable for historical provenance via service-role reads; a binding row can never grant authority — it is routing/identity/provenance data on a service-role-only table, and every action independently passes membership/authority/policy gates;
  - **uniqueness:** `unique(organization_id, source_system, binding_kind, external_id)` as the base rule, **plus a global partial unique on `(source_system, binding_kind, external_id)` for routing-critical kinds** (`legacy_organization_key`, `gu_whatsapp_number`, `legacy_lead`, `legacy_user`) — inbound event routing must resolve an external id to exactly one Organization; kinds not source-guaranteed org-exclusive stay org-scoped only. Kind registry (with its uniqueness class) lives in `packages/types`.
  Plus verification/provenance jsonb.
- `contacts` — id uuid, organization_id, minimal display fields (name, primary phone hint), `preferences_jsonb` (provenance-carrying entries for S2 contact-scoped preferences), created/updated. **No legacy-lead mirror fields** — contact truth stays referential; one contact ↔ n `legacy_lead` bindings ↔ n Opportunities (S1 cardinality).
- `organization_feature_flags` — organization-scoped rollout flags (TD-2b).
- `organization_tool_secrets` — organization-scoped provider credentials (TD-5; same AES-256-GCM crypto helpers as the CURRENT `account_tool_secrets`, which stays untouched).

**Multi-seat WRITE authorization.** All writes to org-owned business rows go through server routes using service-role helpers that call a deterministic `authorizeOrgAction(actorUserId, organizationId, action)` check (membership + role/grant) before mutating; user-JWT direct writes to org business tables are **not** enabled in R1 (matching the CURRENT server-route architecture). RLS: new org tables get membership-EXISTS **SELECT** policies + service-role-only write policies; the only user-writable new table is `portfolio_presentation_state` (TD-9), which gets user-scoped write RLS. Consequential decisions persist actor + role at decision time (approvals already do; admission/authority operations will too).

**Organization-aware access matrix (RLS does NOT inherit through FKs, and PERMISSIVE policies OR-compose, so adding policies alone cannot revoke the legacy `user_id` path on org-owned rows).** Strategy: **permissive + RESTRICTIVE composition**, fully additive — CURRENT policy definitions are never touched. Two new policies per user-readable Case surface: (P) a permissive membership-SELECT path, and (R) an `AS RESTRICTIVE … TO authenticated` **org-tenancy guard** that ANDs across every permissive path: `organization_id IS NULL OR is_active_org_member(organization_id)`. Result: legacy rows (`organization_id IS NULL`) behave byte-identically under CURRENT owner policies; Organization-owned rows are governed **only** by current active Membership — a revoked member is denied even when they are the historical creator `user_id`. `is_active_org_member(org uuid)` is a STABLE `SECURITY DEFINER` helper (checks `organization_memberships.status='active'` for `auth.uid()`), keeping policies simple and avoiding RLS recursion into the memberships table. The restrictive guard targets `TO authenticated` only, so service-role paths are untouched and remain **application-authorized** (`authorizeOrgAction` + explicit `organizationId` helpers) as designed. The alternative — scope-aware re-issue of every existing permissive policy with `AND organization_id IS NULL` — reaches the same end-state but mutates live policies; rejected for brownfield risk, noted as optional later consolidation.

**`is_active_org_member` hardening invariant (approved; binding on implementation).** Every org-owned row's access depends on this one function, so a `SECURITY DEFINER` implementation must: (i) resolve every object, operator and function through a securely fixed `search_path` and/or fully schema-qualified references — never through caller-controlled resolution; (ii) run with least-required execution privileges — `EXECUTE` revoked from `PUBLIC` and granted only to the roles that invoke it, with an owner no more privileged than reading `organization_memberships` requires; (iii) remain safe for invocation from the policies above — `STABLE`, side-effect free, no recursion into the policies it serves. The repo's existing security-definer functions (`handle_new_user` 00001, `match_memories*` 00005/00006/00008/00011) schema-qualify but set **no** `search_path`, so they are a partial precedent only and must not be copied verbatim here. This plan states the invariant; the exact PostgreSQL/Supabase formulation is chosen at implementation time.

| Surface | R1 access strategy |
|---|---|
| `operational_cases` | + (P) membership SELECT (`organization_id IS NOT NULL AND is_active_org_member(organization_id)`); + (R) org-tenancy guard on the row's own `organization_id`; writes server-only |
| `case_facts`, `case_artifacts`, `case_approvals`, `operational_case_events`, `case_subjects`, `case_subject_external_refs` (TD-14) | + (P) membership SELECT **via parent-case subquery**; + (R) guard evaluated against the **parent Case's** `organization_id` (`EXISTS (SELECT 1 FROM operational_cases c WHERE c.id = case_id AND (c.organization_id IS NULL OR is_active_org_member(c.organization_id)))`); writes server-only; CURRENT user policies untouched |
| `work_items` / `work_item_attempts` | **server/service-role only in R1** — portfolio work summaries are server-rendered through authorized helpers; no new RLS (defense-in-depth deferred until a user-JWT read path exists) |
| `case_relationships`, `organization_policies`, `organization_feature_flags` | (P) membership SELECT + service-role writes (org-owned from birth ⇒ no legacy path, no restrictive guard needed) |
| `external_identity_bindings`, `external_conversation_bindings`, `source_events`, `external_effect_operations`, `organization_tool_secrets`, `resource_usage_events` | **service-role only** (operational/security internals; never exposed to user JWTs) |
| `contacts` | (P) membership SELECT + service-role writes |
| `portfolio_presentation_state` | user-scoped RLS with **membership required on writes**: SELECT `user_id = auth.uid()`; INSERT/UPDATE WITH CHECK `user_id = auth.uid() AND is_active_org_member(organization_id)` — `user_id = auth.uid()` alone is insufficient |
| Work Portfolio queries | server-side service-role + `authorizeOrgAction` + explicit org filter; authorization resolved before any ranking/model context (AC-9) |

**RLS negative-test suite (release-gating, §8):** (1) creator with active membership → allowed; (2) another active member → allowed; (3) creator whose membership was revoked/deactivated → **denied** on the org-owned Case and all its children; (4) legacy `organization_id IS NULL` row → CURRENT owner access preserved exactly; (5) active member of a *different* org → denied; (6) presentation-state write by a non-member of the referenced org → denied.

**Bootstrap:** migration + script create `organizations` + a `legacy_organization_key` binding, and memberships are supplied separately (below). `profiles.business_brain.identity.organization_id` is a **discovery source, not the key**: legacy-source verification established that its stored form is the raw Firestore path (`users/<ownerUid>`) while the normalized organization identity is the **bare owner UID**, so the binding's `external_id` carries the normalized UID and the raw path is persisted as provenance in the same statement. Nothing routes on the raw form. **Inbound WhatsApp routing is a separate external identity** and binds as `gu_whatsapp_number` — never as `legacy_organization_key`, which anchors identity rather than routing events. **Membership is never inferred from the discovery profile:** the profile a legacy identity happens to be found on (e.g. a development profile pointed at the pilot's legacy context) does not become a member; every seat is named explicitly with an explicit role, and platform authority (`is_ungga_admin`) is independent of any Organization role (§6). The JSONB field becomes a read-fallback until SL-0 completes (mirrors the repo's `data_sources.warehouse` transition pattern).
**Alternatives rejected:** full RLS/tenancy rewrite (big-bang; rejected by ADR-106); org-in-JWT-claims-only (no membership truth, no impersonation-safety — the legacy audit's acting-context lesson); contacts-as-JSONB-on-case (breaks S1 continuity lookup and P0-4 cardinality).

### TD-2 — Versioned Organization Policy (ADR-108)
**Recommendation.** One table `organization_policies` (organization_id, policy_type from a typed registry in `packages/types` — first type `relationship_admission`, second `relationship_engagement`; version ≥1; status `draft|validated|published|archived`; `policy_jsonb` structured; `nl_intent_source` retained as provenance; published_by/at) with **published-row immutability + delete-protection triggers copied from the `workflow_definitions` pattern (CURRENT precedent, 00065)** and partial unique (org, policy_type, version).
Deterministic resolver in `packages/agent/src/policies/` (queries in `packages/db`): input = typed semantic interpretation (model output, structured) + context; output = typed result (`allowed | blocked | requires_human | clarify`) + matched rule path + **effective version attribution** persisted on the consuming decision (case event payload / fact provenance). A **platform Recommended baseline** ships as a versioned code constant (`platform-default@<n>`) used when the org has no published policy — itself conservative; missing/invalid policy never widens authority (fail-closed).
NL conversational authoring is a later slice; R1 starts with the seeded Recommended baseline + a minimal inspection surface.
**Alternatives rejected:** extending `engagement_policy_overrides_jsonb` (user-scoped, unversioned, unauthorized — rejected by ADR-108 itself); policy-as-workflow-definition rows (conflates process authority with permission authority).

### TD-2b — Organization-scoped rollout flags
**Problem.** The CURRENT `account_feature_flags` seam is per-user; R1 behavior is Organization-owned. If authority-bearing behavior were resolved per member, two advisors of one org could receive conflicting admission/effects/authority modes.
**Recommendation.** New table `organization_feature_flags` (organization_id, flag_key, enabled, value_text, unique(org, flag_key)) + resolver `getOrganizationFlagValue(db, organizationId, key)`. **Every R1 authority-bearing flag resolves at organization scope only** — never per member, never with a per-user fallback: `relationship_ops`, `relationship_admission_mode` (`shadow|assisted|live`), `relationship_send_effects` (`off|approval_only|policy`), `relationship_appointment_effects`, `relationship_runtime_authority_transfer`, `legacy_event_ingestion` (`poll|webhook`). Per-Opportunity runtime authority remains the case column (TD-3): the org flag gates whether transfer is *permitted*; the case column is the per-Opportunity truth. `account_feature_flags` remains for genuinely user-scoped features; env vars remain global kill-switches (repo doctrine).
**Alternatives rejected:** nullable `organization_id` on `account_feature_flags` with XOR scope (one table, two resolution semantics — easy to misuse); convention "flag lives on the owner seat" (implicit, breaks on seat changes/impersonation).

### TD-3 — Runtime & conversation authority (ADR-107)
**Recommendation.** Two representations, matching the two scopes:
- **Runtime decision authority** = additive nullable `operational_cases.runtime_authority` (`legacy | gu_os`; default `legacy` for relationship cases). Per-Opportunity, set only by an authorized governed operation; never implied by Case creation.
- **Conversation authority** = fields on the external conversation binding (TD-4): `conversation_authority` (`gu | human_active`), `last_human_activity_at`, `authority_source` provenance. Legacy `bypass_bot` signals map in via ingestion (C1) as evidence; `advisor_wa` observations are evidence only (audit §9.1.1) and never auto-transition authority.
- **Resolver:** shared TS function `resolveInteractionAuthority(org, externalRefs)` used by every pre-effect gate, plus an internal endpoint `POST /api/legacy/authority` consumed by the legacy router (cross-repo C2) — authenticated per the **TD-13 signed service contract** (not a shared static bearer), first in log-only/advisory mode, then enforcing. Unknown/conflicting authority ⇒ fail-safe: no autonomous external effect, surfaced as an operational incident (case event + notification).
- Authority transitions are recorded as case events using the CURRENT `state_changed`/`human_decision` types with `payload.kind = "authority_changed"` (TD-11 — no CHECK migration needed).
**Alternatives rejected:** generic authority-lease table (over-engineered for one migration dimension; ADR-107's reevaluation trigger covers it); authority inside `context_jsonb` (unqueryable, unauditable); collapsing conversation authority into the binding status enum (different lifecycle/audit semantics — AC-4).

### TD-4 — External conversation bindings (generalize, don't mutate 00044)
**Recommendation.** New table `external_conversation_bindings`: organization_id, case_id, contact_id, provider (`whatsapp_business`), external_conversation_ref (opaque; legacy `lead_id` and/or provider thread id), gu_channel_identity (Gu/WABA number binding ref), thread_kind (`gu | advisor_wa`), conversation-authority fields (TD-3), status, provenance, partial-unique active per (case, provider, external_conversation_ref). The CURRENT internal `operational_case_conversation_bindings` (web/telegram, `chat_id bigint`, user-scoped) stays untouched.
**Rationale:** different semantics (external participant, org tenancy, opaque string refs, authority fields); zero risk to live internal routing. **Alternative rejected:** widening 00044's CHECK + reusing `chat_id bigint` (type mismatch, user-scoped RLS, routing-code coupling).
**`advisor_wa` bindings are evidence-only:** conversation-authority fields are valid **only** on `thread_kind='gu'` rows — enforced by a CHECK (authority columns null when `thread_kind='advisor_wa'`) and by the TD-3 resolver ignoring advisor threads for authority. Advisor-thread rows exist purely to bind captured off-thread evidence (audit §9.1.1) to the Case/contact.

### TD-5 — Operational gateway & fresh-read capabilities (AC-1) — hybrid target
**Capability surface.** A gateway module `apps/web/src/lib/legacy-gateway/` (adapters + normalization + org-binding checks) surfaced to the model **only** as bounded semantic tools in the CURRENT `TOOL_CATALOG`/adapter pattern: first wave `legacy_lead_get_context`, `legacy_lead_get_recent_messages` (thread-aware: Gu + `asesor_*` docs, `source`, `delivery_status` per item — audit §10.1/§15.7), `appointment_get`, `property_get_details` (reusing existing EasyBroker/Ungga read seams where they already exist). No generic CRUD tool, ever. The capability contract is the durable interface; the adapter behind each capability is replaceable.

**Adapter strategy — comparison:**
| Criterion | (a) Legacy-side read APIs | (b) Direct Firestore/Mongo adapters | (c) Hybrid (b bootstrap → a target) |
|---|---|---|---|
| Least privilege / blast radius | Endpoint-scoped, auditable | **Weak for Firestore**: GCP IAM has no per-collection read grants and Admin SDK bypasses security rules → one credential reads the whole database. Mongo Data API keys can be role/collection-scoped (better) | Bootstrap accepts bounded risk read-only, shadow-only; target restores least privilege |
| Latency / freshness | +1 hop, fine | Best | Both acceptable |
| Brownfield coupling / drift | Legacy team owns schema behind a contract | Gu OS couples to messy physical shapes (`wsp_messeges`, multi-representation leads) that moved 24 commits in 3 days | Drift alarms during bootstrap; contract-stable at target |
| Operational ownership | Clear (legacy team) | Split/implicit | Explicit handover point |
| Cross-repo dependency | Serializes all reads behind legacy work | None | Shadow slices unblocked; C6 due before effects |
| Replaceability | n/a | Hidden by capability layer | Designed-in |

**Recommendation: (c) hybrid.** Direct read adapters are sanctioned **only as shadow/bootstrap**: read-only credentials (Mongo keys collection-scoped; the Firestore credential documented as whole-database read — an explicitly accepted, time-boxed, shadow-only risk), collection allowlist in code, org external-binding check before every read, provenance on every result, and **contract-fixture tests + drift alarms** (fixture shape mismatches page an operator, mirroring the divergence-triage pattern). The **durable target is bounded legacy-side read APIs — cross-repo contract C6** (lead context, messages, appointment, property reads), which replace adapters per capability without semantic change.
**Gate (HUMAN DIRECTION):** **C6 is a hard gate before SL-9 — the first prospect-facing external-effect stage.** There is **no production risk-waiver path** permitting direct Firestore/Mongo bootstrap adapters to support assisted or selective-live effects: once any prospect-facing effect is enabled, pre-effect freshness reads (message send and appointment capabilities) run exclusively on the C6 bounded path, and direct adapters are retired from effect-serving paths (they may persist only behind shadow-stage flags).

**Credentials:** dedicated `organization_tool_secrets` (TD-1) with providers `traditional_gu_firestore` / `traditional_gu_mongo` / later `traditional_gu_api`; CURRENT `account_tool_secrets` untouched.

**Event ingestion (wake-ups):** webhook `POST /api/legacy/events` authenticated per **TD-13** + `source_events` inbox table (organization_id, source_system, event_kind — first classes: inbound prospect message, advisor activity/takeover signal, appointment change, assignment change; external refs; **unique dedup_key**; allowlisted payload; claim/lease processing columns copied from the CURRENT `telegram_webhook_updates` pattern) → normalize → resolve org/contact/Opportunity via bindings → `next_action_at = now()` + case event. Legacy-side forwarding is cross-repo contract **C1**; until it ships, a bounded **interim polling adapter inside the gateway** (encapsulated, per AC-1 §6.7) drives shadow slices.
**Alternatives rejected:** (a)-first (serializes shadow work needlessly); (b)-as-target (blast radius + drift, above); BigQuery for anything live (AC-1); standing sync/mirror into Postgres (Brief non-goals).

### TD-6 — External effects: `send_prospect_message`, appointments & the effect ledger (AC-2)
**Recommendation.** Hybrid: **Work Item Attempts remain the execution/evidence root**, plus one **generic `external_effect_operations` ledger** modeled on the CURRENT `publication_operations` (00063) but cross-capability: organization_id, case_id, work_item_id/attempt_id, capability (`send_prospect_message | appointment_write | …`), **operation_key** (logical idempotency identity, unique per capability), status `claimed | running | succeeded | failed | unknown_outcome`, provider_refs_jsonb (`wamid`, appointment ids), evidence/timestamps.
**Rationale:** attempts are per-try and cannot carry cross-retry logical identity; `publication_operations` proves the claim/`unknown_outcome`/reconcile semantics but is publication-shaped and live — generalizing a **new** table keeps it untouched (migrate it in later, if ever). **Alternatives rejected:** attempts-only (no stable idempotency identity across retries); per-capability ledger tables (n× the same DDL); mutating `publication_operations` in place (live-consumer risk).
**`send_prospect_message` capability:** deterministic pre-effect gate (TD-3 authority + TD-2 engagement policy + freshness reread) → claim effect op → transport via cross-repo **C3** (wrapped legacy send endpoint accepting `operation_key`, returning `wamid`) → delivery evidence from `wamid` + the audit-verified Firestore `delivery_status` writeback read (§15.7) + optional callback forwarding (**C4**); `unknown_outcome` ⇒ reconciliation work, never blind resend. First rollout mode: **prepare + approval for every send** (assisted stage), autonomy widened per policy only after evidence.
**Appointment execution is IN R1.** Rationale: under `runtime_authority = gu_os` with legacy suppression (C2), a prospect's visit request must be executable by Gu OS — S2/P0-3 name visit coordination as routine autonomous-capable work and R1's graduation evidence is visit progression. Capabilities `appointment_create | appointment_reschedule | appointment_cancel` follow the same TD-6 pattern (pre-effect gate → effect op with `operation_key` → transport → evidence → reconcile), transported via cross-repo **C7**: a wrapped internal endpoint over the **existing legacy appointment flow** (audit §11: billing reserve/confirm/cancel + Google Calendar + dual Firestore/Mongo persistence — replicating that orchestration with direct writes from Gu OS would be reckless; wrapping preserves it). Reconciliation handles the audit-verified partial-persistence and orphan-Calendar outcomes; resulting visit truth lands as TD-14 facts. Own slice: **SL-10 (assisted)**, prerequisite to SL-11. **Degraded mode (HUMAN DIRECTION):** if C7 slips, the only permitted fallback is an **explicit, time-bounded pilot degradation** with `relationship_appointment_effects = off` and S2 human-as-executor booking (Gu coordinates, advisor executes in the legacy UI). This mode **does not count toward R1 graduation** of autonomous Visit coordination and **never widens authority** (no alternative write path is opened).

### TD-7 — Case relationships & lineage (ADR-109) — sequenced early
**Recommendation.** One table `case_relationships`: organization_id, from_case_id, to_case_id, relationship_type from a small typed registry in `packages/types` (initial: `duplicate_of`, `superseded_by`, `split_from`, `transaction_association`; directed except association), status active|ended, created_by/actor + reason/evidence refs, provenance, partial-unique active edge per (from, to, type); membership RLS; mutations only through an authorized helper in `packages/db` that never touches either case row (ADR-109 §4); relationship events appended to both cases' timelines (payload.kind).
**Sequencing:** the **primitive (table + registry + helper) lands in the substrate wave (SL-0)**; **duplicate canonicalization + supersession flows land immediately after admission (SL-3)** — S1 shadow acceptance scenarios (EC-06, AC-15) exercise duplicates from the first real lead traffic. `transaction_association` **usage is in R1 via TD-16/SL-8b**. Deferred post-R1: human-reviewed merge/split data-movement flows (S1 §17).

### TD-8 — Relationship semantics on the kernel (S1/S2/S3)
- **Case type & definition:** register `lead_opportunity` in `operational_case_types` + seed a **minimal published global workflow definition v1: a single durable state (`open`) with a completion contract and no business-stage transitions** — progression lives in facts (AC-7: no `current_step`), while satisfying two CURRENT kernel constraints: case definition pinning, and `work_items.workflow_definition_version NOT NULL`. Root skill via `default_skill_slug`.
- **Fact-key namespace — settled incrementally, by the Slice that first needs each part:** `opportunity.objective`, `opportunity.requirements.*`, `opportunity.viability`, `opportunity.closure` (outcome/reason/evidence per S1 §8.10), `progression.<milestone>` (evidence-attributed, repeatable). Ownership, replacing the earlier blanket “finalized in SL-2/SL-8”: the **admission-relevant keys are settled by SL-2** — `opportunity.objective` and `opportunity.viability`, landed and Done 2026-09-06; the **canonical `opportunity.closure` representation and the closure reasons required for duplicate and supersession are settled by SL-3** (human ownership decision, 2026-09-06 — §11), as one canonical typed / registry seam later Slices consume — **landed 2026-09-07 in `packages/types/src/opportunity-closure.ts`**; the **visit / progression vocabulary is settled or extended in SL-8** where its approved behavior requires it. **SL-8 consumes SL-3's canonical closure vocabulary** and may extend the controlled reason registry only where required — never a second or parallel closure representation. `opportunity.requirements.*` remains unsettled until a Slice actually needs it. **Visits and Commitments are `case_subjects` (TD-14)** with subject-scoped facts and clean keys (`visit.occurrence`, `commitment.due` — no entity ids inside `fact_key`). Supersession + provenance are the CURRENT `case_facts` mechanics.
- **Admission (S1):** model semantic interpreter (skill) → structured admission proposal → **deterministic executor**: TD-2 policy resolution, contact/legacy-lead dedup via bindings, idempotency on the source-event dedup_key, then CREATE / ATTACH / CLARIFY / DO-NOT-ADMIT with disposition event + facts. Shadow mode writes everything but triggers no prospect-facing work.
- **Case Supervisor (S2):** root skill `lead-opportunity-supervisor` running under the CURRENT case-runner (`channel: case_runner`), per-wake sequence: compile context (facts + open work + commitments + fresh gateway reads + policy + authority) → diagnose → posture (no-op/wait/research/work/human modes) → inline reads or durable Work Items (**first consumer of `work_items.origin='agent_proposed'`**, bounded by allowed capabilities + deterministic adapter-side policy/authority checks — dynamic planning never widens authority) → set `next_action_at` or quiesce with a reconstructible re-entry path. - **Evidence gaps/reconciliation:** ordinary facts + Work per AC-8/S3 §13.7 — no gap subsystem.

### TD-13 — Cross-repo service authentication
**Problem.** `/api/legacy/events` and `/api/legacy/authority` are an authority-sensitive multi-tenant boundary; a single static shared bearer (CRON_SECRET-style) gives no service identity, no purpose scoping, no rotation without simultaneous cutover, and no replay resistance.
**Recommendation (TENTATIVE contract `LegacyServiceAuth` v1):** per-service, per-purpose **HMAC request signing** — headers `x-guos-key-id`, `x-guos-timestamp`, `x-guos-signature` = HMAC-SHA256(secret, method + path + timestamp + body-hash). Properties:
- **Service identity & scope:** each key id names one calling service and one purpose (`events-ingest`, `authority-read`, `delivery-callback`); an events key cannot call the authority endpoint.
- **Organization/capability binding:** each key id is bound server-side to the org(s)/source-systems it may speak for; payload org claims are validated against the key's binding, never trusted.
- **Replay semantics (authenticity and semantic idempotency deliberately separated):** the HMAC + ±5-minute timestamp window provides **authenticity, integrity and freshness only** — there is **no signature cache** (a process-local cache is invalid under multiple app instances; a shared/durable one adds infrastructure without need). Within-window replay of a signed request is rendered harmless because **every endpoint is semantically idempotent via durable Postgres state**: **C1** events — `source_events.dedup_key` unique (duplicate delivery collapses, at-least-once safe); **C2** authority — read-only stateless recomputation of *current* state (replay returns current truth; rate-limited per key); **C3/C7** effects — `external_effect_operations.operation_key` unique (replayed command resolves to the existing operation); **C4/delivery callbacks** — provider-id dedup (`wamid`/status id unique on evidence recording; effect-op status transitions are idempotent; `resource_usage_events.event_key` unique). This is the simplest contract that stays safe under multiple application instances.
- **Rotation:** two active key ids per service/purpose with overlapping validity; rotation = add new, drain, revoke old — no coordinated cutover.
- **Operations:** secrets server-side only (env/secret manager, never client), audit log of key id + purpose per request, rate limits per key, request-size caps; IP allowlisting optional hardening.
**Alternatives rejected:** static bearer (above); mTLS or OAuth client-credentials (stronger but disproportionate operational load on the legacy VM estate for R1 — reevaluate if the surface grows). The webhook-signing pattern is already familiar on the legacy side (it consumes Meta's signed webhooks).

### TD-14 — Case Subjects & subject-scoped Facts (full kernel contract, code-verified)
**Alternatives compared:**
- **(A) Pure structured facts, entity id inside `fact_key`** (`visit.<uuid>.occurrence`). Rejected: accidental schema in a string key; per-visit reads need prefix scans; enumeration means key parsing.
- **(B) Full `case_visits` entity with lifecycle columns.** Rejected: reintroduces the mutable single-status record S3 §12.1 forbids and duplicates fact provenance/supersession mechanics.
- **(B′) `case_facts.subject_kind + subject_id` columns + per-kind identity tables.** Rejected: `subject_id` cannot carry a real FK when each kind has its own table — recreating the polymorphic-integrity problem at column level.
- **(C) Generic `case_subjects` registry + single FK — RECOMMENDED.**

**The primitive (immutability structural, not conventional).** `case_subjects`: `id uuid PK`, `case_id FK`, `subject_kind` (typed registry in `packages/types`; R1 kinds: **`visit`**, **`commitment`**), `label`, `attrs_jsonb` (minimal at-creation identity attributes, e.g. the Visit's property external ref + source), `created_at/created_by`, provenance. Rows are **structurally immutable identity anchors**: no-UPDATE/no-DELETE triggers (the `evidence_records` pattern), zero lifecycle columns; all lifecycle/evidence lives in facts. Plus `unique(id, case_id)` as a composite-FK target. On `case_facts`: one additive nullable column `subject_id uuid` with **composite FK `(subject_id, case_id) REFERENCES case_subjects(id, case_id)`** — a subject fact structurally cannot point at another case's subject. `subject_kind` lives on the subject row, not on facts.

**Organization is derived, never independently supplied.** `case_subjects` carries **no `organization_id`**: tenancy is owned by the parent Case (`operational_cases.organization_id`, M-CASE-ORG) and the `case_id` FK makes that parent link structural, so a cross-tenant mismatch has no surface on which to occur. The kernel already contains this exact pattern: `operational_case_events` carries no tenant column and its CURRENT policy resolves ownership through a parent-Case `EXISTS` subquery. (The other Case children — `case_facts`, `case_artifacts`, `case_approvals`, `artifact_inputs` — instead denormalize the tenant key as `user_id` with an `auth.uid() = user_id` policy, so the kernel supports both shapes; derivation is chosen here because it removes the mismatch surface entirely, and it is how the TD-1 access matrix already governs these rows.) The cost is a per-row subquery in the child policies, so `operational_cases(id, organization_id)` is indexed and plans are re-checked as volumes grow. Org-scoped reads (portfolio projections, reverse lookup from an external ref) join `operational_cases`, which is the authorization order §6 requires anyway. **If a later access path genuinely requires the denormalized column**, it may be added only as a structurally constrained value and never as an independently supplied one: `case_subjects (case_id, organization_id) → operational_cases(id, organization_id)` and `case_subject_external_refs (subject_id, organization_id) → case_subjects(id, organization_id)`, each requiring the corresponding composite unique key on its parent. No second tenancy mechanism is introduced either way.

**Late external references (a Visit exists before its appointment/Calendar/provider ids are known).** Append-only child **`case_subject_external_refs`**: `subject_id + case_id` composite FK → `case_subjects(id, case_id)` (same-case structural; organization derived through Subject → Case, so this table carries no `organization_id` either), `source_system`, `ref_kind` (`legacy_appointment | calendar_event | provider_message | …`, typed registry), `external_ref` (opaque), per-row provenance (`source_kind/source_ref/recorded_by/recorded_at`), **unique `(subject_id, source_system, ref_kind, external_ref)`** — attachment is idempotent (re-discovery is a no-op insert conflict), immutability trigger-enforced (no UPDATE/DELETE). Conflicting or superseded references simply coexist as rows with provenance; S3 domain reconciliation interprets which currently binds (e.g. legacy appointment-id mutation on reschedule ⇒ a second ref row, same subject — continuity preserved). Alternatives rejected: subject-scoped Facts for refs (a growing ref *set* fits the one-current-value-per-key supersession model poorly); surgical jsonb-append trigger (fragile prefix verification, no per-ref provenance). Access: service-role writes; membership SELECT via parent case (TD-1 matrix).

**Kernel contract, resolved against CURRENT code:**
1. **Fact identity & supersession** (`packages/db/src/queries/case-facts.ts`): identity becomes `(case_id, fact_key, subject_id)` with NULL meaning case-level. `insertCaseFact` gains optional `subjectId`; the prior-row lookup adds the subject predicate (`IS NULL` when absent, `= subjectId` when present) — so two `visit.occurrence` facts under different Visits **never supersede or collapse into each other**, while every existing caller (subjectId undefined) matches only NULL-subject rows and behaves byte-identically. The code-managed supersession + last-wins-repair philosophy is preserved unchanged; no unique constraint is introduced (matching CURRENT design).
2. **Query APIs:** `getCurrentCaseFacts(db, userId, caseId)` **keeps its exact signature and semantics by restricting to `subject_id IS NULL`** — its Map<fact_key, fact> contract is only collision-free under that restriction, and every existing consumer (impact snapshot, supervisor context, S1 facts) means case-level facts. New APIs: `listCaseSubjects(db, userId, caseId, kind?)`, `getCurrentSubjectFacts(db, userId, caseId, subjectId)` (Map keyed by fact_key within one subject — collision-free by construction), and `listCurrentSubjectFactsByKind(db, userId, caseId, kind)` for projections (rows grouped per subject).
3. **Impact Plane / ImpactSnapshot** (`impact-engine.ts`, `impact-plane.ts` — code-verified): `ImpactSnapshot.facts` is keyed by bare `fact_key`, and `impact_dependencies` / `approvals[].evidence_inputs` are **static strings inside published immutable definitions** — they structurally cannot name per-instance subjects. Decision: **subject-scoped facts are not addressable as impact/evidence inputs in R1.** The snapshot builders (`buildCaseImpactSnapshot`, `bindImpactPlaneStore.getCurrentFacts`) continue to read case-level facts only (which the restricted `getCurrentCaseFacts` gives them for free) — **zero changes to `impact-engine.ts`**, no artifact-staleness or approval-evidence hashing ambiguity, no possibility of two Visits colliding inside an evidence hash. Subject-fact "staleness" is a domain concern handled by S3 reconciliation Work, as approved. If a future domain needs artifact dependencies on subject facts, that is a later generic evolution of the input-ref grammar (e.g. an aggregate `fact:<key>@<kind>` form) — explicitly deferred, not smuggled in now.
4. **`recordCaseFactsAndApplyImpact`** gains optional `subjectId`: when present, the no-op comparison consults the subject's current facts (not case-level), writes flow through `insertCaseFact` with the subject, and the **impact-engine pass is skipped** (a subject fact can never be a declared input, and running it would falsely match a same-named case-level dependency key). When absent: existing behavior, unchanged.
5. **Approval/evidence hashing:** unaffected by construction (point 3): `buildCaseApprovalEvidence` snapshots remain case-level. R1's send/appointment approvals pin their basis in the effect-operation payload + approval snapshot, not in subject facts.
6. **Indexes:** keep the CURRENT `idx_case_facts_current (case_id, fact_key) WHERE superseded_by IS NULL`; add partial `idx_case_facts_current_subject (case_id, subject_id, fact_key) WHERE superseded_by IS NULL AND subject_id IS NOT NULL`; `case_subjects (case_id, subject_kind)`.
7. **Append-only trigger:** unchanged — the existing `to_jsonb(old) - 'superseded_by' = to_jsonb(new) - 'superseded_by'` comparison automatically makes `subject_id` immutable post-insert.
8. **RLS:** `case_subjects` and `case_subject_external_refs` follow the child-table pattern (TD-1 matrix).

**Visits on the primitive:** stable Visit identity = subject row; multiple Visits = multiple rows; reschedule continuity = same subject + superseding `visit.schedule` fact (analytics: 1 visit, n schedule changes — S3 §9.3); property change ⇒ new subject (S3 §9.5) + disposition fact on the old one; evidence/provenance/conflict = unchanged `case_facts` mechanics; querying/analytics = joinable registry, no key parsing. **Commitments on the primitive:** `commitment.<uuid>.*` had the same accidental-schema flaw — commitments become `case_subjects(kind='commitment')` with facts `commitment.expected_outcome`, `commitment.actor`, `commitment.due`, `commitment.status`; the S2 taxonomy (commitment ≠ Work Item ≠ scheduled reconsideration) is untouched. **`commitment.due` value shape** (clarified 2026-09-11): `{ due_at, basis, due_expression }`, with **exactly one of `due_at` and `due_expression` non-null**. `due_at` is written only from a full ISO-8601 datetime with an explicit offset or `Z`, normalized to UTC; any timing that does not name an instant — natural language, a date without a time, a time without a zone — is **preserved verbatim as `due_expression`, never resolved**, because nothing in R1 governs which reference time or timezone would resolve it and resolving it without one would fabricate a deadline. `basis` (`stated | inferred_from_context`) records provenance **independently of resolution** — a timing can be both stated and unresolved. Enforcement is at the deterministic producer boundary, not the judge schema: a schema failure discards the whole proposal, commitments included. S2 is unchanged by this — it requires commitments to preserve their timing semantics, which is exactly what `due_expression` does when the timing is not an instant.

**Why generic:** one cross-domain identity primitive (visits, commitments today; Transaction documents, Demand ads tomorrow) with a single real FK and a same-case composite guarantee — consistent with the Brief §5.13 design test and AC-7. It is a shared-kernel extension approved **with this plan** (human direction, Appendix A).
